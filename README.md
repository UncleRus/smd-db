# SMD-DB

Веб-интерфейс поиска по базе SMD-деталей. Одна страница поиска с фильтрами,
отдельная страница детали и страница «О базе». Интерфейс на английском,
русском и китайском; три темы оформления (iron / neon / dust).

Приложение построено на **Flask** (WSGI-фреймворк) и **Jinja2** (шаблоны).

Данные и оформление — из исходных материалов без изменений:

- `smd.sqlite` — копия `materials/smd.sqlite`, открывается **только для чтения**;
- `app/static/elumkit/` — байт-в-байт оригиналы дизайн-системы elumkit
  (`packages/core-css/src`). Собственные стили приложения лежат отдельно в
  `app/static/app.css` и подключаются **после** elumkit.

## Требования

- Python 3.11+
- Зависимости рантайма из `requirements.txt`: Flask 3.1+ и Jinja2 3.1+.
- Продакшен-сервер — uWSGI (см. «Развёртывание»); встроенный сервер Flask
  используется только для отладки.

## Запуск (dev)

```bash
cd build
python3 -m venv .venv                     # если .venv ещё нет
./.venv/bin/python -m pip install -r requirements.txt
./.venv/bin/python run.py
```

Приложение поднимается на <http://127.0.0.1:5000/>. Остановить — `Ctrl+C`.

Сервер запускается с `threaded=True`: каждый запрос обслуживается в отдельном
рабочем потоке и получает собственное соединение с SQLite (см. ниже).

> `run.py` — встроенный сервер Flask, он **только для отладки**. В продакшене
> приложение разворачивается на **uWSGI за nginx** (см. «Развёртывание»).

## Развёртывание на rpi41 (uWSGI + nginx)

Встроенный сервер Flask не предназначен для продакшена: его заменяет
**uWSGI**, а входным прокси служит **nginx**. Готовые файлы лежат в `deploy/`.

Дерево `build/` разворачивается как есть в `/opt/smd-db/`:

```
/opt/smd-db/
├── app/                    пакет с шаблонами и статикой
├── tests/
├── deploy/                 uwsgi.ini, smd-db.service, nginx-smd-db.conf
├── run.py                  dev-сервер (не используется в продакшене)
├── wsgi.py                 WSGI-точка входа (wsgi:application)
├── smd.sqlite              база (read-only)
└── .venv/                  окружение
```

### Установка

```bash
# на rpi41
sudo apt-get install -y uwsgi-core uwsgi-plugin-python3   # uWSGI из дистрибутива

cd /opt/smd-db
python3 -m venv .venv
./.venv/bin/python -m pip install -r requirements.txt     # Flask + Jinja2
```

uWSGI берётся готовым из дистрибутива (`/usr/bin/uwsgi` + плагин `python3`), из
исходников ничего собирать не нужно. Плагин собран под системный Python;
виртуальное окружение, созданное тем же Python, указывается директивой
`virtualenv` в `deploy/uwsgi.ini`.

### systemd и nginx

```bash
sudo cp deploy/smd-db.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now smd-db

sudo cp deploy/nginx-smd-db.conf /etc/nginx/sites-available/smd-db
sudo ln -s /etc/nginx/sites-available/smd-db /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

- `deploy/uwsgi.ini` — uWSGI: `plugins=python3`,
  `virtualenv=/opt/smd-db/.venv`, `chdir=/opt/smd-db`,
  `module=wsgi:application`, `processes=4`, `threads=4`,
  `enable-threads=true`, сокет `127.0.0.1:5000`. Каждый запрос получает
  собственное соединение с SQLite, поэтому и процессы, и потоки безопасны.
- `deploy/smd-db.service` — unit systemd (пользователь `smd-db`, журнал в
  `journalctl -u smd-db`, секреты — через `/etc/smd-db.env`).
- `deploy/nginx-smd-db.conf` — обратный прокси на uWSGI.
- Обязательно задайте `SMD_SECRET_KEY` в `/etc/smd-db.env` — им подписывается
  сессионная cookie.

## Тесты и проверки качества

```bash
cd build
./.venv/bin/python -m pip install -r requirements-dev.txt   # pytest, mypy, ruff, black
./.venv/bin/python -m pytest        # 48 тестов
./.venv/bin/python -m mypy          # mypy --strict, конфигурация в pyproject.toml
./.venv/bin/python -m ruff check app run.py wsgi.py tests
./.venv/bin/python -m black --check app run.py wsgi.py tests
```

Тесты работают без запуска сервера: `create_app()` возвращает `flask.Flask`,
который тестовый клиент (`app.test_client()`) дёргает напрямую. Обращения к
слою данных из тестов выполняются внутри `with app.app_context()`.

## Маршруты

| Метод | Путь                          | Назначение                                   |
|-------|-------------------------------|----------------------------------------------|
| GET   | `/`                           | Поиск и результаты                           |
| GET   | `/part/<int:part_id>`         | Страница одной детали                        |
| GET   | `/package/<pkg:code>/image`   | PNG-чертёж корпуса (BLOB из БД); 404, если чертежа нет |
| GET   | `/about`                      | Страница «О базе»                            |
| GET   | `/static/...`                 | Статика (elumkit, `app.css`, `app.js`)       |

Код корпуса может содержать косые черты и зарезервированные символы. Для
маршрута чертежа заведён url-конвертер `pkg` (`views.PackageCodeConverter`):
входящий путь принимает косые черты, а генерируемый URL кодирует все символы
вне unreserved-набора (`quote(code, safe="")`).

## Рендеринг и механизмы Flask

- **Роуты** живут в `app/views.py` (Blueprint `main`). Вид читает запрос,
  спрашивает `Catalogue`, строит ссылки и **сам рендерит** шаблон через
  `rendering.render` — тонкий слой без логики в шаблонах.
- **Jinja-окружение** настраивает `rendering.configure_environment(app)`:
  фильтр `num` (группировка тысяч), глобаль `t` (перевод) и `finalize`,
  который рисует `None` пустой строкой.
- **`t`** — единственный запрос-зависимый хелпер: читает `request`/`session`
  сам и установлен глобалью Jinja. Общие данные страницы (`lang`, `theme`,
  `languages`, `themes`, `page_sizes`, `stats`, `active`) приходят из контекста.
- **`app/services.py`** — сервисный слой: `Catalogue` владеет разбором
  параметров поиска и превращает низкоуровневые запросы `app/db.py` в
  постраничный `SearchResult`.
- **`app/config.py`** — настройки (`SESSION_TIMEOUT`, `PAGE_SIZES`,
  `DEFAULT_PAGE_SIZE`); `create_app()` копирует их в `app.config`, откуда их
  читает сервисный слой через `current_app.config`.

URL строит вид: `views.py` собирает ссылки навигации, сброса, перехода к
детали, пагинации, переключателя языка, чертежа корпуса и статики и кладёт их
в контекст готовыми строками — шаблоны URL не конструируют (`url_for` в них
отсутствует). Пути берутся из Flask-функции `url_for` (маршруты по именам
эндпоинтов, без захардкоженных путей), а query-строка собирается отдельно —
Werkzeug оставляет часть зарезервированных символов (`/`, `?`, `*`, скобки) в
значениях query незакодированными, поэтому её кодирует `urlencode` из
`urllib.parse`; так ссылки остаются предсказуемыми и корректными.

Язык и тема разрешаются в `rendering.py`: query-параметр → сессия → значение по
умолчанию; результат кэшируется на `flask.g` один раз за запрос. В сессию
значение пишется **только** при явной передаче параметра, поэтому обычный
запрос (в том числе 404 статики) cookie не выставляет.

Ошибку рендерит `app/errors.py`: обработчик `HTTPException` рисует 404
(и прочие HTTP-ошибки), обработчик `Exception` — 500. Оба возвращают
`(html, код)`, поэтому исходный код ответа сохраняется; используется тот же
`rendering.render` и общее оформление `error.html`.

## Доступ к базе данных: соединение на контекст

SQLite привязывает соединение к создавшему его потоку, а сервер
многопоточный (dev-сервер с `threaded=True`, uWSGI с `threads`). Приложение
поэтому не полагается на толерантность драйвера (`check_same_thread=False`) и
не делит одно соединение между запросами:

- **`app/database.py`** открывает **по одному read-only соединению на запрос**
  и хранит его в `flask.g` (`file:<path>?mode=ro`, `PRAGMA query_only = ON`).
  Соединение создаётся лениво при первом обращении и закрывается хуком
  `teardown_appcontext` (`close_db`). `check_same_thread` остаётся включённым
  по умолчанию.
- Так как соединение создаётся и используется внутри одного потока, разные
  рабочие потоки получают разные соединения и ничего не разделяют. Это и
  обеспечивает корректное обслуживание параллельных запросов; тесты
  `test_database_connection_is_per_context` и `test_concurrent_requests_are_served`
  проверяют это напрямую (в том числе 8 одновременных запросов).

`app/db.py` — только SQL: фильтры, сортировки и запросы. `get_db()`
берёт соединение текущего контекста, а `stats()` кэширует счётчики каталога по
resolved-пути базы, так что смена каталога сбрасывает кэш.

## Страницы ошибок

Ошибки любого рода — 404 неизвестного маршрута, отсутствующей детали, корпуса
или файла статики, а также внутренняя ошибка 500 — выводятся на странице
`error.html`: тот же navbar, тема, язык, футер и оформление elumkit, что и у
остальных страниц. Код ответа (`404`/`500`) сохраняется, трейсбек
пользователю не показывается. Текст локализован (EN/RU/ZH) и берётся из
текущей сессии/параметров запроса.

## Параметры поиска (`/`)

Все параметры хранятся в URL, поэтому ссылка на результаты адресуема. Пока не
задано **ни одного** условия, таблица результатов не выводится — страница
показывает форму и подсказку начать поиск; полный каталог не выгружается.

| Параметр       | Значение                                                      |
|----------------|---------------------------------------------------------------|
| `code`         | Маркировка (подстрока, регистр не важен; спецсимволы — буквально) |
| `name`         | Название (подстрока, регистр не важен)                        |
| `function`     | id функции                                                    |
| `manufacturer` | id производителя                                              |
| `package`      | код корпуса                                                   |
| `pins`         | число выводов                                                 |
| `sort`         | `marking` \| `name` \| `manufacturer` \| `package`            |
| `per`          | размер страницы: 20 \| 50 \| 100                              |
| `page`         | номер страницы                                                |
| `lang`         | `en` \| `ru` \| `zh`                                          |
| `theme`        | `iron` \| `neon` \| `dust`                                    |

Язык и тема сохраняются в подписанной cookie-сессии Flask, поэтому после
перехода без параметров выбранное оформление и язык сохраняются.

## Замечания по данным

- Поиск по маркировке — по **подстроке** кода и без учёта регистра: `L3`
  находит 840 записей (полное совпадение дало бы 62).
- Спецсимволы в кодах (`?`, `+`, `/`, `\`, `_`, `%`, `*`) трактуются
  буквально, а не как маски `LIKE`/`GLOB`: `%` — это подстрока в 14 записях,
  а не «все строки».
- Чертежи корпусов лежат в `packages.image`. У части корпусов картинки нет
  (`image IS NULL`) — вместо битой картинки интерфейс рисует собственную
  заглушку (inline SVG, знак `?` из `currentColor`, читается в любой теме).
- FTS не используется: фильтры по `LIKE` и точному совпадению по 440 234
  строкам укладываются в десятки миллисекунд, а схема БД при этом не меняется.
- Соединения с базой выдаются на запрос и закрываются по его завершении; база
  всегда открывается в режиме `mode=ro` с `PRAGMA query_only = ON`.
